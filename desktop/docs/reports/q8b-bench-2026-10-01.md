# Radxa Dragon Q8B — the frame contract, 2026-10-01

The first numbers from a slow machine, for comparison with the i7-12700KF /
RX 6750 XT. Measured by `abyss/tests/bench-metronome.sh` (three runs) and by
`undertow run --backend auto --frames 300` on the real display (five runs,
one of them `fathom --measure`, whose report is
[next to this](fathom-radxa-computer-co-ltd-radxa-dragon-q8b.txt)).

## The machine and how it was run

- Qualcomm Snapdragon 8cx Gen 3 (SC8280XP): 4 × Cortex-X1C + 4 × A78C,
  16 GB; Adreno 690 through the board port's `msm` (render) and `msmfb`
  (KMS) drivers. FreeBSD `radxa-dragon-q8b` at `afe542b98a`, drm-msm-kmod
  `0f23f29` (docs/boards/radxa-dragon-q8b/).
- Desktop: monorepo `desktop/` at `cdcd933`, debug build (what the scripts
  and the installed binaries use), Swift 6.3.3.
- `power_profile=balanced` (powerd adaptive, C-states to C3, GPU devfreq on),
  the default. The desktop session was stopped; the machine otherwise idle.
- Display: DP-1 1920×1080 @ 60 Hz through the board's DP-to-HDMI bridge, the
  hardware vblank clock (DRM).

## Against the i7-12700KF / RX 6750 XT

- **Composite cost is not the problem.** p99 is 18–21 µs on the display and
  under 100 µs headless with 512 surfaces, against a 2 ms budget: the slow
  CPU costs nothing measurable at this load.
- **Missed flips: a few per run here, none there.** The i7's saved report
  (58 of 300) predates the five P4.5 fixes; after them it held **0 of 1800**
  at a ~2 ms margin (BACKLOG §3). The Q8B misses 0–5 of 300 (≤ 17‰) with
  margins of 2.7–6.4 ms — more margin, not less, yet still misses.
- **Every run has exactly one present event delivered 18–25 ms late** —
  more than a period. That looks like the board's `msmfb` flip-completion
  path (its vblank handling, or the DRM event's delivery), not `undertow`;
  it's the first thing to chase before reading the misses as the
  compositor's. Real-time priority didn't change it (runs 1–2 against 3–4).

## What `fathom` couldn't ask on arm64

- **Boot:** `machdep.bootmethod` exists only on amd64 and i386; an arm64
  FreeBSD machine boots by UEFI (or by a DTB-only loader), so the probe reads
  "could not be read" on every arm64 machine.
- **Wi-Fi:** `net.wlan.devices` exists only once `wlan` is loaded; a machine
  without wireless and without the module reports "could not be asked"
  instead of "absent".

Both are in BACKLOG §5.
